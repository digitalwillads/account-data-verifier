The account-data verifierchecks the pull,not the business.

This follows Verifiers judge the business, tools read the world. It covers one verifier that checks only data reading. Its own tree calls it "the spec of the Rust pull." Here is what it checks, what reads it, and a proposal.

From Will, written with Claude, October 16, 2026.

What it checks

Its purpose: "Every client's data is pulled every day, is complete and true, and is kept, so every manager and every check works from the real picture." For each day's snapshot, it asks:

NumberThe checkWhy it matters
1Every live client is pulled todayA client left out gets no flags, so nobody looks at it.
2Fresh, or marked old with a reasonOld numbers shown as today's hide a problem.
3A failed read is a warning, never zeroA $0 from a failed read looks like a quiet day.
4Inside the shared API limit15,000 Google Ads operations a day, shared with every push.
5The numbers match the platformSame days, in the account's own time zone.
6No day is missingA missing day can fake a spike or a drop.
7Only conversions the client countsA page view as a lead makes cost per lead look good.
8"Unanswered" is really unansweredGmail labels decide it. A draft is never a message.
9A person's changes are seenAlso Editor changes, which the API change log misses.
10Each day's data is keptAn audit needs the data as it was that day.

Two more goals cover issues on live items only and the notebook's shape. A check that cannot run never passes.

Why it is a tool check

Will drew the line today: verifiers judge the business logic and the shape of an issue. They do not judge data reading or the AI's own functions. The pull is a tool. It is act pull (code in data/src/pull/), in Will's verifiers repo today, ported from the old desk pull. So these checks are really the pull's own tests. If the pull tests itself and marks bad data, we need no separate verifier.

What reads it today

  • The client storyReads its fails with six other verifiers. It runs it again when a fail is older than the client's last pull. verify/src/client_story/
  • The ManagerReads each client's snapshot from the pull. It expects the pull done by 7:15 AM. verify/src/manager/gather/notebook_reads.rs
  • The Verifier auditA fire drill removes one client's file from a day and expects this verifier to catch it. cli/src/verifier_audit/drills.rs
  • Its own runs22 runs since Oct 15. No daily pull job runs now. Each client run pulls its own client. state/account-data/runs

Caution: a false fail comes back

Today, on Will's order, the concurrent-pulls fix (gate change account-data-concurrent-pulls) comes out of the verifiers. It fixed data reading, and that belongs in tools.

When two pulls run at once, they write one pull.log. Reads are then counted for the wrong run, and quota-safe fails by mistake. Real case: Trailer Jacks on Oct 15 and 16, 7 reads counted as 2. Barbara's client automations start together. KDX and Kogalla start at 7:00 AM. AAFE, KeyBar and Trailer Jacks start at 8:45 AM (as of Oct 16). On Oct 16, four pulls started within 31 seconds at 8:46 AM. So the next runs bring the false fail back.

A proposal

Will has not decided.

  1. Keep the verifier until its checks become the pull's own tests. Then retire it.
  2. Give each pull run its own log.
  3. Stagger the run start times, or make the pull safe to run in parallel.
